# Security status

Vale is an unaudited experiment, **not a production-safe or guaranteed anonymous messenger**. Do not use it for sensitive data. No formal review or physical-device security test has been performed.

## Cryptography and identity

Each identity is an Ed25519 key pair. For a message, keys are converted to X25519 and `crypto_box_beforenm` derives a shared secret. HMAC-SHA-256 derives a direction- and application-specific XChaCha20-Poly1305 key. A random 192-bit nonce is generated per packet. A versioned canonical header (ID, sender, recipient and timestamps) is authenticated as AEAD associated data; the header, nonce and ciphertext are signed with Ed25519. Receivers verify signature, limits, lifetime and known sender before decryption; packet IDs are retained for replay suppression. This custom protocol has not been reviewed or proven secure and provides **no forward secrecy or post-compromise security**. Users must authenticate contact keys out of band.

## Networks and metadata

LAN transport uses bounded TCP frames to private/link-local/loopback IPv4 destinations. Android Nearby Connections additionally discovers peers using Google Play services over available Bluetooth and Wi-Fi radios. LAN is enabled by default; Nearby and relaying are opt-in. These transports may expose metadata or device presence. A relay must know both endpoints and is opt-in, with a hop limit. Routing headers expose public IDs, timestamps and packet sizes to peers and relays; LAN also exposes IP addresses. Incoming resources are bounded, but malicious peers can still cause denial of service. There is no background delivery, guaranteed delivery, congestion control or read receipt. A successful delivery receipt is an Ed25519 signature by the destination over the packet ID and endpoints, after the destination accepts and stores it; relays forward the signature and cannot forge it. This does not prove that a person read it or that a compromised destination will retain it.

Tor-only mode binds the listener to loopback and sends only v3 onion destinations through the bundled local SOCKS proxy, using SOCKS domain-name requests rather than local DNS. It does not fall back to LAN or Nearby; direct WebRTC calling is disabled. The onion service's secret key is stored in app/account-private Tor files, not the encrypted database. Tor can be blocked, has no bridges configured here, and cannot protect against compromised endpoints, traffic analysis or a user sharing identifying information. The same long-term public ID is used across transport modes and permits cross-mode correlation. Local applications under the same account may access Tor or the loopback media bridge. Switching modes cannot retract traffic or address disclosures that already occurred.

## Media, storage and SOS

Media is handled by a local HTTP bridge bound to loopback. Requests require an unguessable per-session token and a matching Host/Origin; this is not protection from a compromised browser, extensions or local account. Recording uses browser/device codec support. Calls use direct, host-only WebRTC with encrypted SDP signaling but no TURN; the peer learns network addresses and NAT traversal may fail. Calls are disabled in Tor-only mode. When switching to Tor during an active call, the app first requires a browser acknowledgement that its peer connection has stopped; close the call tab if it does not respond. SOS cannot forcibly close an external browser tab: close it manually. Media validation is bounded and checks basic format signatures, not a full malicious-file audit.

On Android the database is SQLCipher and its random passphrase is wrapped by a non-exportable Android Keystore AES-GCM key. On Windows SQLite3MultipleCiphers uses SQLCipher v4 and a DPAPI-protected passphrase. Unlocked accounts, compromised OS, process memory, backups and contacts can expose data. Expiry is best-effort deletion, not secure erasure. The calculator is concealment, not authentication or a wipe.

APK debug signatures and the unsigned Windows installer are unsuitable for a production trust chain. Tor/other dependencies require ongoing patching and supply-chain review. Report security issues privately to the repository owner; do not post keys or sensitive messages in public issues.
